## 2. 测试目标

本轮不验证医学效果，主要回答以下产品与工程问题：

1. 用户是否能在没有额外教学的情况下理解“收缩、保持、放松”？
2. 动画是否能清晰表达不可见的肌肉状态变化？
3. 训练状态机能否严格按照预设顺序和时长运行？
4. 3 组训练是否能完整结束，经验和连击是否正确？
5. Android 真机上的动画、触觉、返回操作和前后台切换是否稳定？
6. Demo 是否达到可继续扩展第二个微游戏场景的架构质量门槛？

本方案不包含登录、云同步、社交、商城、后台管理和真实 AI 接口测试。

## 4. 环境准备与准入条件

### 4.1 真机设置

1. 在手机“关于手机”中连续点击版本号，启用开发者选项。
2. 打开“USB 调试”。
3. 使用支持数据传输的 USB 线连接电脑。
4. 手机弹出 RSA 授权窗口时选择允许，建议勾选“始终允许此计算机”。
5. 某些国产 Android 系统还需打开“USB 安装”或“通过 USB 验证应用”。
6. 测试期间关闭省电模式和游戏加速器，避免其改变动画或触觉表现。
7. 锁定竖屏；当前 Demo 不将横屏作为支持范围。

### 4.2 环境检查命令

在项目根目录执行：

```powershell
adb kill-server
adb start-server
adb devices -l
flutter --version
flutter doctor -v
flutter devices
```

合格标准：

- `adb devices -l` 中存在目标设备，状态为 `device`。
- 不允许出现 `unauthorized`、`offline` 或空列表。
- `flutter devices` 能识别同一台 Android 设备。
- `flutter doctor -v` 的 Android toolchain 不存在阻止构建的错误。

若 `flutter` 长时间停在 `Waiting for another flutter command to release the startup lock`，
先确认没有正在运行的 IDE 构建或 Flutter 命令，再结束残留 Dart/Flutter 进程，并重新执行。
不要在正常构建尚未结束时删除锁文件。

### 4.3 首次生成与依赖检查

```powershell
flutter create --platforms=android,web .
flutter pub get
flutter analyze
flutter test
```

准入门槛：

- `flutter analyze`：0 error；warning 应在测试前评估。
- `flutter test`：全部通过。
- Debug APK 可以成功构建。

```powershell
flutter build apk --debug
```


用于功能验证、日志查看和快速复测。`device-id` 从 `flutter devices` 获取。

```powershell

```

最终交付前再验证 Release：

```powershell
flutter build apk --release
adb install -r build\app\outputs\flutter-apk\app-release.apk
```

```powershell
flutter logs
adb logcat -c
adb logcat | Select-String -Pattern "flutter|AndroidRuntime|FATAL EXCEPTION"
```

发现崩溃时，应保留从启动前 5 秒到崩溃后 10 秒的日志。

### 生命周期产品决策点

当前引擎按真实时间计算阶段进度，因此 APP 在后台时训练可能继续推进。测试需要明确记录：

- 返回后是否跳过了一个或多个阶段；
- 是否直接到达结算页；
- 用户是否感到困惑。

建议验收决策：训练进入后台或锁屏时应暂停，回到前台后显示“继续训练”。
这属于下一轮实现建议，当前轮先作为已知行为评估，不作为崩溃类缺陷。

## 9. 动画与视觉专项测试

### 9.1 动画语义

邀请 3–5 名未看需求说明的体验者，仅告诉他们跟随屏幕完成训练。每个体验者结束后回答：

1. 哪个动画表示收紧？
2. 哪个动画表示保持？
3. 哪个动画表示放松？
4. 是否曾经不知道该做什么？
5. 哪个阶段的节奏过快或过慢？

产品验收建议：

- 至少 80% 的体验者无需解释即可正确识别三个动作。
- 至少 80% 的体验者认为动画和动作方向一致。
- “不知道该做什么”的停顿不得超过一次完整训练中的一个阶段。

## 10. 触觉专项测试

不同 Android 厂商会对 `lightImpact`、`mediumImpact`、`heavyImpact` 做不同映射，因此不要求振幅完全一致。

| 状态 | 预期触觉 | 验收标准 |
|---|---|---|
| 进入 CONTRACT | 无强制触觉 | 不应有意外连续振动 |
| 进入 HOLD | 中等单次反馈 | 只触发一次，可明确感知 |
| 进入 RELAX | 轻微单次反馈 | 比 HOLD 更轻或至少不更强 |
| 单组完成 | 较强单次反馈 | 只触发一次，不连续震动 |
| 最终完成 | 当前无额外反馈 | 不应出现残留振动 |

在系统关闭触觉、静音、勿扰模式和正常模式下各执行一次。任何模式都不得导致崩溃或流程暂停。

## 11. 性能、资源与稳定性

### 11.1 性能测试

使用 Profile 模式，在能代表目标用户的中端 Android 真机上测试。

```powershell
flutter run --profile -d <device-id>
```

打开 Flutter DevTools Performance，录制至少两次完整训练。

验收建议：

- 60 Hz 设备：UI 和 Raster 帧绝大多数低于 16.7 ms。
- 90 Hz 设备：绝大多数帧低于 11.1 ms。
- 120 Hz 设备：以视觉平滑、无连续掉帧为核心，不强制所有帧低于 8.3 ms。
- 不允许出现连续 3 帧以上明显卡顿。
- 状态切换和单组完成时不得出现肉眼可见冻结。
- CustomPainter 不应引发持续内存增长。

### 11.2 稳定性与资源测试

| ID | 优先级 | 操作 | 预期结果 |
|---|---|---|---|
| STB-01 | P0 | 连续完成 10 次完整训练 | 无崩溃、卡死、状态错乱 |
| STB-02 | P1 | 连续进入并中途退出 20 次 | 无计时器泄漏、重复触觉或页面叠加 |
| STB-03 | P1 | 观察 DevTools Memory | 每次退出训练页后内存能回落，无线性增长 |
| STB-04 | P1 | 训练过程中观察 CPU | 无异常持续满核；退出后 CPU 明显下降 |
| STB-05 | P2 | 低电量和省电模式各执行一次 | 允许动画降帧，但流程和计分必须正确 |
| STB-06 | P1 | 旋转设备 | 若系统锁定竖屏则不旋转；否则不得崩溃或布局损坏 |

| ERR-03 | P1 | 训练中改变系统字体或显示大小后返回 | 页面可恢复，无永久遮挡 |
| ERR-04 | P2 | 开启屏幕录制执行训练 | 动画可用，计时误差不明显增加 |
| ERR-05 | P2 | 同时播放音乐或音频 | Demo 不抢占音频焦点 |
| ERR-06 | P1 | 强制停止 APP 后重新打开 | 从首页开始，不直接进入旧结算页 |
| ERR-07 | P1 | 卸载并重装 | 可正常首次启动，无外部数据依赖 |

## 13. 状态机时序测量方法

推荐使用 60 fps 屏幕录像：

1. 开始录屏。
2. 点击“开始训练”。
3. 完成至少一整组。
4. 在视频编辑器中逐帧定位状态标题变化的首帧。
5. 用帧数计算阶段时长：`阶段帧数 ÷ 视频帧率`。

验收误差建议：

- 单阶段允许误差：±150 ms。
- 三组累计训练误差：±500 ms。
- 倒计时数字不允许出现 `0` 长时间停留或负数。
- 切换到下一状态时，进度条必须从新阶段起点重新开始。

## 14. 探索性体验测试

每位体验者完成两轮训练，第一轮不解释，第二轮允许阅读指导。

记录以下 1–5 分指标：

| 指标 | 1 分 | 5 分 |
|---|---|---|
| 动作理解 | 完全不理解 | 无需解释即可理解 |
| 动画反馈 | 与动作无关 | 与身体感觉高度一致 |
| 节奏舒适度 | 明显不适 | 非常自然 |
| 趣味性 | 像普通倒计时 | 有微游戏感并愿意再玩 |
| 科技感 | 粗糙、普通 | 成熟、有品质感 |
| 继续使用意愿 | 不会再用 | 愿意连续体验一周 |

开放问题：

- 最喜欢哪个反馈？为什么？
- 哪个阶段最难理解？
- 核心压缩是否让你自然联想到“收缩”？
- 放松动画是否带来释放感？
- 你希望下一种反馈是气球、花朵、锻造还是机关解锁？
- 是否希望训练中有声音、语音或节拍提示？

Demo 继续迭代门槛建议：

- 动作理解平均 ≥ 4.0。
- 动画反馈平均 ≥ 3.8。
- 趣味性平均 ≥ 3.5。
- 不出现导致训练无法完成的 P0/P1 缺陷。

## 16. 发布验收标准

只有全部满足以下条件，第一版 Demo 才视为通过真机测试：

- 三组训练可以连续完成，结算稳定显示 +30 XP、x3、3/3。
- 训练中退出不会留下仍运行的计时器或持续触觉。
- Profile 模式下没有连续明显掉帧，动画在主测试设备上肉眼平滑。
- 连续 10 次完整训练无崩溃和状态错乱。
- 默认字体和主设备分辨率下没有布局溢出。
- 至少完成一轮未引导用户体验测试，并记录主观反馈。

## 17. 推荐执行顺序

1. 完成真机 USB 授权，使 `adb devices -l` 显示 `device`。
2. 解决 Flutter CLI 初始化卡住的问题。
3. 执行 `flutter analyze` 和 `flutter test`。
4. Debug 模式完成冒烟和全部功能用例。
5. Profile 模式完成动画、性能和资源测试。
6. 执行生命周期、边界和连续 10 次稳定性测试。
7. 邀请 3–5 名体验者完成探索性体验测试。
8. 修复 P0/P1，复测关联流程。
9. Release 包完成一次最终冒烟。

第一轮执行时，优先完成 P0/P1 用例；P2/P3 可在核心流程稳定后补测。
